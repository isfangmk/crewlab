### 4.18 Redis 强依赖 + 多 worker + 对话流多订阅者续接（已实施 · 2026-11-17）

> 状态：**已实施**，分 6 个阶段提交（commit e37773c → e5f02cf → 4def1c6 → 9383927 → bb8171e → 阶段5）。按用户最新决策：Redis 为**强依赖**（不保留进程内回退）、全量替换内存态协同、**同时上多 worker**、用户自备本地 Redis。

**背景与前提判断**：改造前是单 uvicorn worker、单进程架构——主聊天流是 request-scoped SSE 直连 ADK runner（连接一断产出就停，第二标签页只能开新回合），两个事件总线是模块级 dict + `asyncio.Queue`，停止信号/渠道锁/运行态注册表全是单进程语义，前端 `chatLiveBus` 是单标签 `window.CustomEvent`，跨页靠 5s 轮询。Redis 的价值以多 worker/多标签为前提，故全量接入。

**运行环境**：Windows Redis `tporadowski/redis` 5.0.14.1，路径 `C:\Users\admin\Downloads\Redis-x64-5.0.14.1`，绑定 127.0.0.1:6379；`scripts/service.ps1 start redis` 纳管。`REDIS_URL` 为必填配置，连不上启动失败。

**实现约束（遵守）**：
- 根因修复：生产/消费解耦在编排层收口，全部协同经 `app/redis` 单例，禁止散落 `redis.from_url`；无进程内回退（强依赖）。
- 公开接口不变：两个事件总线签名与 SSE 端点逻辑不动，仅换底层 transport。
- Redis 只做协同与帧分发：权威业务数据仍在 DB；通知只带「信号」不带大数据（图表等仍走 artifacts + SSE）。
- 禁 mock、真依赖验证；不改 UI 设计规范；每阶段中文 commit；无表结构变更，不写数据修复脚本。

**多 worker 的平台限制（实测结论）**：Windows 上 uvicorn 多进程 supervisor 让各 worker 在共享监听 socket 上再调 `listen()`，Windows 不支持 → `OSError WinError 10022`，实测 2 worker 只有 1 个存活（health 200 具误导性）。`uvicorn.exe` 与 `python -m uvicorn` 均如此，是平台限制而非代码问题。本地默认单 worker；架构已在阶段 2–4 全量 Redis 化，真正的多 worker 在 Linux 部署，`UVICORN_WORKERS=N` 启用。

**验证结果（真依赖，禁 mock）**：
1. Redis `ping`=PONG；后端带 `REDIS_URL` 启动、healthz 200；连接单例可用。
2. 核心场景：真浏览器两标签页同对话，A 发消息、B 中途打开 → B 补发进行中帧并续推；A 断连不中断生产；API 层双订阅者拿到完整帧流。
3. 事件总线：两进程 publish/subscribe，backlog 补发 + 实时续推全收到；相关 e2e/workflow pytest 真 Redis 全过。
4. 锁与共享状态：锁唯一性、错值无法释放他人锁、跨 worker 停止信号经 PubSub 实际送达 stop_check、leader 选举单实例——5 项真 Redis 验证全过。
5. 通知：真登录 + 真 Redis + 真 SSE 端到端（backlog 补发 + kind 正确）；真浏览器两标签，后端发通知后另一端 window 事件即时触发（非轮询）。
6. 静态：ruff + basedpyright 0；前端 tsc + eslint 0；只跑相关 pytest（禁全量）；验证数据/脚本结束即清理。

**已知限制（如实记录）**：
- 生产者所在 worker 崩溃则该回合后台生产消失（未做任务持久化/重调度）；Redis Stream 保留已产出帧，前端可读到断点。
- Windows 无法本地多 worker（见上）；多 worker 收益需在 Linux 部署兑现。
- Stream 靠 MAXLEN + TTL 权衡回溯窗口与内存；大 payload 仍走 artifacts 表，不塞 Redis。
