## 1. HIGH

### H1 — 密钥脱敏漏掉 JSON 形式

**位置**：`backend/app/logging_setup.py:12-13`

```python
(re.compile(r"(api[_-]?key\s*[=:]\s*)(\S+)", re.IGNORECASE), r"\1***"),
(re.compile(r"(password\s*[=:]\s*)(\S+)", re.IGNORECASE), r"\1***"),
```

`\S+` 会连引号一起吃掉，但要求 `key` 与值之间**没有引号**。实测：

```text
输入: payload {"api_key": "AKIA-not-sk-value", "password": "hunter2"}
输出: payload {"api_key": "AKIA-not-sk-value", "password": "hunter2"}   ← 未脱敏
输入: api_key=abc123 def
输出: api_key=*** def                                                  ← 已脱敏
```

真实可达路径：`llm_admin.probe_chat` 把上游响应体放进 `detail`（`llm_admin.py:127`），`chat_service.stream_session_message` 记录完整用户输入（`chat_service.py:491-503`）。用户若在消息里粘贴带 `api_key` 的 JSON，会原样进日志。

**修法**：脱敏正则必须同时覆盖 `key="value"` / `key: "value"` / `key=value` 三种形态，且只替换值部分保留引号。

### H2 — MCP credential 明文存储、明文回吐、且从未用于认证

**位置**：`backend/app/services/mcp_service.py:29`（回吐）、`:215`（存库）、`:88-97`（连接参数）

```python
# server_to_wire：明文给每个 API 客户端
"credential": s.credential,

# connection_params_for_server：credential 完全没参与
headers = _parse_headers(server.header_template_json)
```

三个独立问题：

1. **明文回吐**：`GET /mcp/servers` 把原始 credential 交给任意 bearer token 持有者。对比 `llm_admin.list_llm_settings` 会返回 `********` 掩码 —— 同一仓库两套标准。
2. **明文存储**：`mcp_servers.credential` 是 `String(256)` 明文列。仓库已有 `secrets_service`（Fernet 加密 + 凭证库）却未用于 MCP。
3. **从未用于认证**（最严重）：`connection_params_for_server` 只注入 `header_template_json`，credential 列被完全忽略。

结合前端 `web/src/pages/Mcp.tsx:931-946` 可确认设计意图：**credential 存的是「凭证库里的凭证名」，不是密钥本身**；`header_template_json` 里的 `{{token}}` 占位符应由该凭证的字段填充。但后端既没有做占位符填充，也没有把 credential 名解析为实际 header —— **配了认证的 MCP server 实际是裸奔连接的**。

**修法**：

- `server_to_wire` 不再回吐 credential 名以外的任何敏感信息（凭证名本身可保留，因为它是引用而非密钥）。
- 建立「credential 名 → secrets 库 → 明文字段 → 填充 `header_template_json` 的 `{{field}}` 占位符」的真实链路，并在 `connection_params_for_server` 中注入。
- 缺凭证 / 缺字段 / 占位符无法解析时**显式失败**。

### H3 — 审批名单与运行时工具名规则不一致

**位置**：`backend/app/services/mcp_service.py:56-73` vs `backend/app/services/agent_service.py:236-243` vs `web/src/pages/Agents.tsx:890`

三处对 MCP 工具名的定义各不相同：

| 位置 | 规则 | 例子 |
| --- | --- | --- |
| `mcp_service.mcp_tool_wire_name` | `mcp__{server}_{tool}` | `mcp__demo_tools_get_health` |
| `agent_service.mcp_server_names_from_tools` | `split("__")` 取 `parts[1]` | 期望 `mcp__{server}__{tool}` |
| 前端 `Agents.tsx:890` | `mcp__{server}__{tool}` | `mcp__demo_tools__get_health` |

后端 `mcp_tool_wire_name` 用**单下划线**连接 server 与 tool，前端（写入用户助理白名单）用**双下划线**。而 `agent_service` 的 `split("__")` 在单下划线名 `mcp__demo_tools_get_health` 上切出 `["mcp", "demo", "tools_get_health"]`，`parts[1] == "demo"` —— 提取出的 server 名被**截断**，与真实 server 名 `demo_tools` 不符。

后果：`filter_mcp_servers_for_agent` 按错误的名字过滤，MCP server 被静默排除；或助理白名单里 `mcp__demo__x` 与运行时实际工具名 `mcp__demo_x` 对不上，`confirm_tool_names` 永远不命中 → **非 trusted MCP 工具跳过审批直接执行**。

**修法**：单一权威命名函数（后端 `mcp_service` 导出），前后端共用同一规则；`agent_service` 用同一个解析函数而非自己 `split("__")`。契约不符时显式失败。

### H4 — `PATCH /chat/sessions/{id}` 恒 422，会话重命名失效

**位置**：`backend/app/api/chat.py:68-81`、`backend/app/schemas/chat.py:47-49`

```python
@router.patch("/chat/sessions/{session_id}")
async def patch_session(
    session_id: str,
    body: UpdateSessionModelRequest,   # 强制 provider + model
```

前端 `web/src/api/chat.ts:111-116` 的 `renameSession` 只发 `{ title }`：

```typescript
return request<void>('PATCH', `/chat/sessions/${encodeURIComponent(sessionId)}`, { title });
```

实测返回 422 `"provider": Field required`。侧边栏重命名（`ChatLayout.tsx:294`）永远失败并静默显示错误。

**修法**：拆成两个明确契约 —— `PATCH /chat/sessions/{id}` 只接受 `title`（重命名），模型切换用独立端点或同一端点的可选字段联合体。契约必须与前端一致；字段缺失显式失败而不是「凑一个 provider+model」。

### H5 — 异步路径内同步 HTTP 阻塞事件循环

**位置**：`backend/app/services/tool_search_index.py:196-239`、`:288`、`:307`

```python
with httpx.Client(timeout=60.0) as client:
    resp = client.post(url, json=payload)     # 同步阻塞，最长 60s
```

`EmbeddingToolIndex.rebuild()` / `search()` 是 `adk_tool_search` 要求的**同步**接口，被 `SearchableToolset` 在 agent 执行路径上调用：

- `SearchableToolset.__init__` → `index.rebuild(...)`（构造期即阻塞）
- `SearchableToolset._catalog_for_context` → 每次 `search_tools` 调用都 `index.rebuild(...)`
- `EmbeddingToolIndex.search` → `index.search(...)` → 同步嵌入查询向量

这三处都在 FastAPI 的事件循环线程里同步执行 HTTP。**每一轮对话都会把整个后端阻塞住**，直到嵌入服务返回（超时 60s）。并发请求会互相排队。

**修法**：不能简单改成 `async`（`adk_tool_search` 契约是同步的）。正确做法是**预计算 + 预取**：

- 工具向量在 `sync_server_tool_embeddings` 时已全部入库（`mcp_tool_embeddings` 表），运行时**不应重新嵌入工具**——直接读库里的向量。
- 查询向量是唯一必须实时嵌入的量，把它挪到 `async` 边界：在 `chat_service` 装配阶段预取，或用 `asyncio.to_thread` 把同步嵌入包起来，让阻塞发生在工作线程而非事件循环。

## 2. MEDIUM

### M1 — 审批先落库再校验，失败后永久卡死

**位置**：`backend/app/services/approval_service.py:128-140`

```python
row.status = "approved" if confirmed else "rejected"
await db.commit()          # ← 先提交

tool_result: dict | None = None
if session.agent_id is None or session.agent_id == "":
    raise LookupError(...)   # ← 后校验，失败时状态已落库
```

提交后该行不再是 `pending`，`_decide` 再次调用会抛 `ValueError("审批状态不可决策")` —— 这张审批单**永远无法再被批准或拒绝**。

**修法**：所有前置校验（session 存在、`agent_id` 绑定、agent 存在、model 可解析、toolset 可装配）必须在写状态**之前**完成；执行失败应写入 `status="failed"` 并保留原因，而不是把状态置为已决却没执行。

### M2 — 审批恢复用错模型、丢失 LLM 超时

**位置**：`backend/app/services/approval_service.py:128`、`:170`；`backend/app/adk_runtime/stream_bridge.py:540-560`

三处不一致：

1. **模型不对**：审批恢复用 `session.provider` / `session.model`，但 `chat_service.stream_session_message` 允许**单回合覆盖** `provider` / `model`（`chat_service.py:463-465`）。覆盖生效时发起工具调用的模型与恢复时用的模型不是同一个。
2. **超时丢失**：`build_chat_agent` 有 `llm_timeout_seconds` 参数（设置页 `agent.llm_timeout_seconds`），但 `stream_adk_confirmation` **没有该参数**，`build_chat_agent` 用默认值 120。审批恢复永远用 120s，配置不生效。
3. **思考开关写死**：`thinking_enabled=False` 硬编码，配置项对该路径无效。

**修法**：把「本回合实际使用的 provider / model / timeout / thinking」持久化到审批单（`Approval` 表加列），审批恢复时读取该记录，保证与发起时一致。

### M3 — 未探测的 enabled server 让所有对话 500

**位置**：`backend/app/services/mcp_catalog_toolset.py:57-59`、`backend/app/services/mcp_service.py:117-121`

```python
if server.status != "ok":
    raise ValueError(f"MCP Server {server.name} 状态不是 ok ...")
```

`build_searchable_mcp_toolsets` 为**每一个** enabled server 构造 toolset。任一 server 启用但没探测过 → 构造抛 `ValueError` → `build_chat_agent` 失败 → **所有对话 500**，与那个 server 无关。

`confirm_tool_names_for_servers` 同样对 `status != "ok"` 抛错。

**修法**：启用状态与探测状态必须分离 —— enabled 但未探测的 server 应被**显式跳过并记日志**（该 server 不可用），而不是让整个对话失败；或者在启用动作上强制先探测（`create_server` 已经这么做，`update_server` 改 `enabled=True` 时应该同样强制探测）。

### M4 — `Runner.close()` 从不调用，MCP 会话管理器泄漏

**位置**：`backend/app/adk_runtime/stream_bridge.py:519`、`:575`

```python
runner = Runner(agent=agent, app_name=APP_NAME, session_service=session_service)
# 之后既没有 async with，也没有 finally: await runner.close()
```

已安装的 ADK 源码确认：`Runner.close()`（`google/adk/runners.py:2279`）是唯一会执行 `_cleanup_toolsets` → `toolset.close()` → `MCPSessionManager.close()` 的路径。`run_async` 不会关闭 toolset。

后果：**每一轮对话泄漏一个 `MCPSessionManager`**，以及它打开的 MCP HTTP 会话。长时间运行后连接数持续增长。

**修法**：`stream_adk_turn` / `stream_adk_confirmation` 用 `try/finally` 包住生成器体，在 `finally` 中 `await runner.close()`。

### M5 — ADK 自建引擎永不释放

**位置**：`backend/app/adk_runtime/session_store.py:19-25`、`backend/app/main.py:57`

```python
_adk_sessions = DatabaseSessionService(db_url=settings.database_url)
```

`DatabaseSessionService` 用 `db_url` 构造时会**自己 create_async_engine**（已核对 `google/adk/sessions/database_session_service.py:346`）。`main.py` 的 lifespan 只 `await engine.dispose()`（业务库引擎），ADK 那个引擎的连接池在进程退出时不会被释放，连接数对 PG 翻倍。

**修法**：改用 `DatabaseSessionService(db_engine=engine)` 复用业务引擎（ADK 支持该重载），或在 lifespan 退出时显式 dispose ADK 引擎。

### M6 — 前端每回合发的 `mentions` / `locale` 被静默丢弃

**位置**：`backend/app/schemas/chat.py:34-42`、`web/src/api/chat.ts:370-372`

```typescript
if (opts.mentions && opts.mentions.length > 0) body.mentions = opts.mentions;
if (opts.locale) body.locale = opts.locale;
```

`StreamMessageRequest` 没有这两个字段，Pydantic 默认 `extra="ignore"` 静默丢弃。实测 `model_dump()` 里没有 `locale` / `mentions`。

`locale` 是前端拿到英文回答的机制（`ChatThread.tsx` 传 UI 语言），后端却只用全局 `agent.output_locale` 设置 —— 用户选 English 但系统设置是 zh，行为与前端预期不符且**无任何报错**。

**修法**：所有请求模型加 `model_config = ConfigDict(extra="forbid")`，让契约不符立刻 422；同时决定 `locale` / `mentions` 的去留 —— 要么后端实现并接受，要么前端停止发送（不能继续发一个被静默丢弃的字段）。

### M7 — Fernet 密钥派生自 `AUTH_TOKEN`，轮换即永久丢数据

**位置**：`backend/app/services/secrets_service.py:65-67`

```python
digest = hashlib.sha256(get_settings().auth_token.encode("utf-8")).digest()
return Fernet(base64.urlsafe_b64encode(digest))
```

`AUTH_TOKEN` 同时是**登录口令**和**数据加密密钥**。轮换登录口令 → 所有已存 `fields_ciphertext` 永久不可解（Fernet 不可恢复）。运维为了安全轮换 token 是常规操作，这里等于删库。

另外 `fields_ciphertext` 在全代码库**无人读取** —— `inject_env` 映射（`:33`、`:43-46`、`:56-59`）是死元数据，凭证库目前存了却不能为任何真实依赖供给凭据（这也是 H2 里 MCP 认证链路缺失的根因）。

**修法**：加密密钥独立配置项（如 `CREDENTIAL_ENCRYPTION_KEY`），与登录 token 解耦；并把解密 + 注入路径真正接通（MCP header 填充靠它）。

### M8 — 保存空 `api_key` 会清掉已存密钥

**位置**：`backend/app/services/llm_admin.py:216-238`

```python
row.enabled = False
row.api_key = ""
```

前端 `LLM.tsx` 的提示是「留空 = 该提供商不出现在聊天页下拉里」，但后端把已存的 key **物理删除**（不可恢复），且 `default_provider` 设置仍指向这个刚被禁用的 provider，`/aiops/models` 随即因为 `get_default_selection` 抛错而 409。

**修法**：空 `api_key` 的语义是「禁用」，只改 `enabled`，**保留已存 key**；同时禁用时检查 `default_provider` 是否指向它，是则显式报错或原子切换。

### M9 — MCP 重名返回 500

### M10 — `tls_insecure` 契约存在但从未生效

**位置**：`backend/app/api/integrations_llm.py:22`、`backend/app/services/llm_admin.py:118`、`:181`

`LLMConfigIn.tls_insecure` 被声明、前端也发（`settings.ts:63`、`LLM.tsx:451`），但从未向下传递，`httpx.AsyncClient` 也没设 `verify=False`。用户勾选「跳过 TLS 校验」后仍会连接失败 —— 一个看起来能用的开关实际是空开关。

### M11 — 空闲会话 stop 返回假成功，并污染下一回合

**位置**：`backend/app/services/turn_control.py:21-27`、`backend/app/api/chat.py:111-121`

```python
def request_stop(session_id: str) -> bool:
    """标记会话停止；返回是否存在可停止的回合标记位（调用方仍应返回 stopped）。"""
    with _lock:
        _stopped.add(session_id)
    return True          # ← docstring 承诺的语义没有实现
```

docstring 说返回「是否存在可停止的回合」，实现恒返回 `True`。空闲会话 stop 会往 `_stopped` 里塞标记；该标记直到**下一个回合**的 `end_turn` 才被清掉 —— 于是下一个回合刚 `begin_turn`（清标记）前的窗口里可能被误停。

**修法**：`turn_control` 显式维护「进行中回合」集合，`request_stop` 只对进行中的回合生效并返回真实结果；空闲时返回 `stopped: false` 或 409。
