# 并行排查 / 计划执行：工作流编排 + UI 定稿对齐方案

> 状态：待确认。确认后按「七、分期」实施。
> 涉及：会话内多子代理排查（并行）与规划执行（串行）两条执行链路及其 UI。

## 一、背景与问题定性

两种模式本质是同一件事：**把一批活拆开跑，等待全部完成，再出汇总结论**。

- 并行排查 = N 路同时推进，等全部收口再汇总；
- 计划执行 = N 步顺序推进，等最后一步完成再汇总。

当前实现的问题：

1. **UI 没按定稿设计稿写**。定稿在 `web/public/design/parallel-serial-ui.html`（并行=跑道式·天蓝、串行=流水线式·紫、计时三口径、自动汇总特写、执行全程零操作按钮），实现偏离了它的结构与视觉。
2. **编排没有归属工作流**。「等待完成后再出结论」靠散落在 `dispatch_service` / `plan_service` 里的 asyncio 任务 + 自维护状态机拼出来，实测暴露：
   - 派发工具有 90s 软截止，到点把「初步结果」交回去——子代理没跑完就不等了，回合文本接着就下结论；
   - worker 起跑后库里状态一直停在 `queued`（只有终态才落库），中途刷新页面状态失真；
   - 会话里的执行与「工作流 / 运行记录」两套互不相认，无法统一回放。

## 二、目标

1. **编排归属工作流引擎**：并行=分支+汇合，串行=顺序链；**结论只在全部完成后产出**——「等待完成」由图结构（join 等全部入边终态）保证，不靠时序约定。
2. **UI 严格按定稿 HTML 落地**：跑道式 / 流水线式双形态 + 计时三口径 + 自动汇总特写 + 全程零操作按钮。
3. 不做旧格式兼容：一步换到新形态。

## 三、方案一：编排收敛到工作流（根因处）

### 3.1 现状机制（为什么会这样）

- `dispatch_investigation` 派发后 `asyncio.create_task` 自管后台任务，`wait_dispatch(soft_deadline=90s)` 到点返回 partial——工具把未完成的中间态当结果交回，模型随即据此下结论；
- `_worker_task` 只在结束写终态，起跑不写 `running`：库里 `queued` 与实际脱节（实测 4 路都在跑、库全显示排队）；
- 计划链 `_run_plan` 同样是自管任务 + 内存信号（stop/pause），收口靠 `_finish_plan` 手工聚合；
- 产品已有工作流引擎（`app/services/workflow/`）：ADK Workflow 图、`join` 汇合节点（多入边等齐）、WorkflowRun / WorkflowNodeRun 持久化、workflow_events 流式推送、run_control 停止、approval / input 人工节点。「等待完成后再出结论」正是它的原生语义，不需要自造。

### 3.2 目标形态

并行排查图（扇出 / 汇合）：

```
start ──► worker_1 ─┐
      ├──► worker_2 ─┤
      ├──►   …     ─┼──► join（等全部入边终态）──► summary ──► end
      └──► worker_N ─┘
```

计划执行图（顺序链）：

```
start ──► step_1 ──► step_2 ──► … ──► step_N ──► summary ──► end
```

- `worker` / `step` = 新增「任务节点」（kind=task），内核复用现有无人值守执行（`build_worker_agent` + `run_headless_turn`）：工具面收窄、聚焦纪律、WorkerBudget 三点不动；
- `join` 等全部分支终态（成功 / 失败 / 跳过都算终态）才放行，一路失败不阻断其他路；
- `summary` = 现自动汇总逻辑（LLM 综合 + 拼接降级 + 幂等写回对话流），从两处 service 的收口分支搬进图节点；
- 计划草稿「用户确认后执行」= `approval` 人工节点（现有能力，不新造）。

### 3.3 关键改动点

1. 工作流节点面新增「任务节点」kind=task（任务执行器复用 headless 引擎）；
2. 会话工具 `create_plan` / `dispatch_investigation` 改为生成工作流定义并启动 run（保留 plan_uid / dispatch_uid 与 run_uid 映射，卡片身份不变）；
3. **取消 90s 软截止返初步结果**：派发工具只返回「已启动 + N 路名单」，不返回任何结论性内容；结论只由 summary 节点在 join 之后产出并自动落对话流（前端 `summary_message_id` → 重拉消息的链路不变）；
4. 状态机补齐：任务节点起跑即写 `running`，修掉「跑着还显示排队」；
5. 运行 / 节点记录复用 `workflow_runs` / `workflow_node_runs`，「运行记录」页统一回放；会话卡片仍走现有 investigation / plan 事件通道（服务端在节点回调里转发，前端不换总线）。

### 3.4 语义承诺

- **等待完成后再出结论**：join 结构保证，不是时序约定；
- 失败路、跳过路不冒充结论，缺口只在 summary 里标注；
- 停止 / 重试沿用现有协作信号，映射为工作流停止与节点重跑。

## 四、方案二：UI 定稿对齐（`web/public/design/parallel-serial-ui.html`）

### 4.1 双形态

| 模式 | 形态 | 配色 | 节奏 |
|---|---|---|---|
| 并行排查 | 跑道式 | 天蓝 sky | 横排分道、每路独立计时、扫光 |
| 计划执行 | 流水线式 | 紫 violet | 竖排编号链+连线、当前步呼吸 |

### 4.2 对齐清单（定稿要素 → 落点）

1. 面板头：kicker（波形图标「并行排查 · 跑道」/ 列表图标「执行计划 · 流水线」）+ 标题 + 副行「开始于 HH:MM:SS · 全程已运行 Xm · N 路同时在跑 / 正在第 k/N 步」；
2. motif 徽记条：并行=每路一轨（done / run / fail / wait 四态填充 + run 扫光）；串行=节点+连线链（done 绿 / run 渐变 / 待跑灰）；
3. 统计行三格：并行「完成 N/M 路 ｜ 工具调用 ｜ 用量 k tok」；串行「进度 k/M 步 ｜ 工具调用 ｜ 用量」；
4. 跑道行：状态徽 + 名称/状态 tag + 目标 + 心跳行（正在调用 X · N 秒前）+ 独立计时（已运行 / 用时）+ 底部 2px 进度条；完成路副行「发现 N 条 · 证据 M 处」；失败行红字错误摘要（如「预算超限：已用 X tokens（上限 Y）」）；
5. 流水线步：编号节点（✓ / 数字 / 呼吸紫 / ✕）+ 连线 + 名称 + 计时或「排队中」+ 结论摘要框（含 web_search ×N、query_knowledge ×N 计数）+ 当前步心跳行（含本步已用 k tok）；
6. 对话内卡片：折叠头（图标 + 名称 + 状态 pill + 计时）+ 分段进度条（每路 / 每步一段）+ 行列表 + 脚注（「跑道式：N 路同时推进，各有时钟」/「流水线式：按序推进，只有一处在跑」+ 最近动作 X 秒前）；
7. 自动汇总消息特写：左紫条 +「✦ 自动汇总」徽记 + 标题「后台排查已全部完成 · N 路收口（x 成功 / y 失败）」+ 正文 [n] 引用角标（点击定位右栏证据）+ 缺口加粗 + 底注（「对结论不满意直接追问『换角度重新汇总』」）；
8. 计时三口径：并行单路计时（已运行 → 用时）、串行当前步计时（排队中不显示时钟）、全程计时（收口定格）；60 秒无日志事件转「疑似停滞」黄色提示；
9. **执行全程零操作按钮**。保留两处例外：草稿态的「调整计划 / 开始执行 / 保存并执行」是执行前动作；失败 / 跳过步骤行内「重试此步 / 跳过并继续」是恢复动作。

### 4.3 样式

- token 进 tailwind：sky / violet / ok / warn / danger 的 soft / line 变体，sweep / grow / pulse 动画按设计稿 keyframes 统一（现有 lane-run 扫光并入）；
- 数字用 `font-variant-numeric: tabular-nums`，全局不用等宽字体（设计稿字体为系统 sans）；
- 明暗两套 token 以设计稿 `:root` 为准。

## 五、数据与边界

- 不做旧格式兼容：前端一次性切新形态，后端 wire 字段按需增删；
- 库表改动直接写脚本（`scripts/db/`），不写迁移代码（规则）；起跑写 `running` 等字段变化同样落脚本；
- token 预算单一源头 `WorkerBudget` 不动（12 步 / 300s / 150k）；
- 提示词不写工具选择路由（规则）：任务节点的能力描述只写产出与推进方式。
