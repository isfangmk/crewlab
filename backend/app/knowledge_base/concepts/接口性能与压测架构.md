# 接口性能与压测架构

本项目用 Locust 对**全部后端接口**做并发压测，从 FastAPI OpenAPI schema 自动反射端点（不手工枚举），对真实后端 + 真库 + 真 Redis 发请求，按端点收集 p50/p95/p99。工具在 `backend/perf/`（用法见 `perf/README.md`）。

## 为什么需要索引：一次真实的慢接口根因

会话列表 `GET /api/v1/chat/sessions` 在 378 会话 / 5848 消息的数据量下，串行 P50 高达 1100ms，10 并发恶化到 6200ms，50 并发到 16000ms。逐条 SQL 计时定位到唯一慢点：

- 默认排序用相关子查询 `_LAST_MESSAGE_AT = SELECT max(created_at) FROM chat_messages WHERE session_id = s.id`（见 `chat_service.py`）。它的语义是「最近有消息的会话排前面」，不能用 `chat_sessions.updated_at` 代替（改名/置顶会误判为最近对话）。
- `chat_messages` 原本**只有主键**，`session_id` 无索引 → 对每行会话都全表扫描 5848 条消息，378 × 5848 ≈ 220 万行 → 单条排序 SQL 1068ms。
- 其他 6 条聚合 / 窗口查询每条都 <13ms，不是瓶颈。

索引 A/B 验证（临时库，不碰真实库）：

| 索引 | 会话列表排序 SQL | 消息列表 `WHERE session_id=? ORDER BY seq` |
|---|---|---|
| 无索引 | 980ms | 4.4ms |
| `(session_id, created_at)` | **0.4ms**（覆盖索引，2400x） | 1.8ms |
| 再加 `(session_id, seq)` | 0.4ms | **0.3ms**（15x） |

两者职责不同、缺一不可：`(session_id, created_at)` 覆盖 `max(created_at)` 聚合（会话排序），`(session_id, seq)` 覆盖消息列表的 seq 排序。

## 已加索引（表结构变更）

模型声明在 `app/models/chat.py` 的 `ChatMessage.__table_args__`（新库自动建），历史库由幂等脚本 `scripts/add_perf_indexes.py`（`CREATE INDEX IF NOT EXISTS`）补：

| 索引 | 列 | 服务查询 |
|---|---|---|
| `ix_chat_messages_session_created` | `(session_id, created_at)` | 会话列表相关子查询 `max(created_at)` |
| `ix_chat_messages_session_seq` | `(session_id, seq)` | 消息列表按 session_id 过滤 + seq 排序 |

**只加了压测证实有收益的两个索引**。`chat_sessions(updated_at)`、`audit_logs(created_at)` 等候选未命中瓶颈，不加（遵守「只做必要变更」）。

## 优化前后对比（同数据量、同参数）

数据：300 会话 / 5000 消息（5 个大会话各 1000 条）/ 20 记忆。纯读压测（写用户权重 0），40s/轮。

| 并发 | 端点 | P50 前→后 | P95 前→后 | 吞吐变化 |
|---|---|---|---|---|
| 1 | 会话列表 | 1125→33ms（↓34x） | 1160→42ms（↓28x） | 25→266 req（↑11x） |
| 10 | 会话列表 | 6242→113ms（↓55x） | 6874→156ms（↓44x） | 62→1928（↑31x） |
| 30 | 会话列表 | 9762→378ms（↓26x） | 12451→605ms（↓21x） | ↑24x |
| 50 | 会话列表 | 16232→635ms（↓26x） | 22827→1106ms（↓21x） | ↑29x |
| 50 | 消息列表 | 10734→468ms（↓23x） | 15373→922ms（↓17x） | ↑26x |

原始报告 `perf/report_before_*.json` / `perf/report_after_*.json`，机器可读对比 `perf/comparison.json`（`perf.compare` 生成）。

## 压测纳入 / 排除

- **纳入读**：所有 GET（SSE/外部网络除外）；**纳入写**：operationId 白名单内、可用 `__perf__` tag 隔离的会话/队列/记忆 CRUD（低权重）。
- **排除**：SSE 长连接、真调 LLM（playground/tools/sandbox run）、skill install/reindex/触发器、登录等——其响应时间不代表接口性能，且烧钱或造不可清理数据。带资源 id 的端点用占位符，走完整路由→鉴权→校验→404，报告 failures 里体现，属预期。
- 数据严格用 `__perf__` tag 隔离，`perf.seed --clean` 精确清理（验证 0 残留），绝不污染用户数据。

## 各页面列表 / 分页接口压测

对 21 个核心列表 / 分页 GET 端点（会话、知识库、可观测、审计、用户、记忆、审批、分享、任务图、工作流、沙盒、提及搜索）跑了同样的串行 + 10/30/50 梯度，报告 `perf/report_lists_*.json`：

- **串行全部 <50ms**（仅 `/knowledge/search` 3–13s、`/audit/export` ~130ms 两个例外），说明各页面列表查询本身没有慢 SQL。
- **并发退化是全局性的、与端点本身快慢无关**：所有端点一起线性退化（10 并发 ~1s、50 并发 ~3.5s）。A/B 对照去掉两个慢端点后，50 并发从 ~3.5s 降到 ~1s、吞吐翻 4 倍——确认拖累源是慢端点占用事件循环 + 单 worker + SQLite 的连接竞争，而非单条查询。即使去掉慢端点，50 并发仍有 ~1s 固有排队，这是本地单 worker（Windows 不支持 uvicorn 多进程 supervisor）的架构上限，不是接口可优化点。

**`/knowledge/search` 慢的根因**：日志显示它每次请求都真调外部 embedding API（`api.siliconflow.cn/v1/embeddings`，`embedding_client.py` 用 `httpx.AsyncClient` 异步但网络延迟不可控），3–13s 波动属外部依赖，不是后端接口或表结构问题。已从常规压测集合 `excluded`（`discovery.py` 的 `_EXCLUDE_PATH_TOKENS`），避免它独占事件循环污染其他端点的并发计时；它仍被单独测过并记录于此。

**`/audit/export`** 默认导出 5000 行 CSV，是管理员偶发操作、非页面分页列表；5000 行的序列化开销属合理范围，不做优化。

## 已知问题（非本次改动，另行处理）

- `test_ask_user_round_trip_in_live_chat` 偶发失败：测试对同一会话连发 3 轮重试，前一轮 cancel ADK session 导致后两轮 `SessionNotFoundError`（日志证据充分）。属真 LLM 测试稳定性问题，与索引改动无关。
- 嵌入式浏览器 SSE 消费停摆（服务端 done 但 UI 仍 busy，刷新恢复）见《常见故障排查》。
